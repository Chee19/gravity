How it gets triggered

Gravity starts only when you type /gravity and your request. Sessions that never type it are untouched.

Install, then setupThe /gravity:setup wizard leaves exactly one workflow on
You type /gravityAnd your request. Nothing else starts it
Router loadsRefused until the wizard has been done
Router classifiesKind x size x risk
Playbook announcedOne line, and you can override it
Ledger startsEvery playbook except Tiny opens a run

Why a typed command: description matching is stochastic, and one public eval saw a test-first skill fire in only 2 of 7 runs on a test-first prompt. A plugin also cannot unload another one mid-session, so the wizard makes sure only one workflow is on.

How the router picks a playbook

Risk means auth, payments, migrations, personal or patient data, or a path in the project's risk list. Work moves up a playbook automatically if it outgrows its size, and Gravity says so out loud.

Skills, agents and commands

Gravity ships exactly one skill. A second skill would be a second router competing for the same request, so everything else is a file the router reads at the right moment. It uses no other plugin's skills.

Inside one task

Each step is done by a script or a fresh agent, so nothing depends on the orchestrator remembering. The dispatch names only file paths, so nothing can get softened in paraphrase.

gravity next says what to do and which file to read
gravity task start records the base
gravity brief assembles the brief from the plan
Fresh implementer commits a failing test
gravity red runs it and records that it failed
Implementer writes the code and commits
gravity gate runs proof, full suite and guards
gravity package builds the diff for review
Fresh reviewer files a verdict
gravity review check confirms each finding is real

When it fails

Round 1Fresh implementer with one consolidated brief
Round 2Must first state the assumption the failed fixes share, and how to test it
Round 3Fresh implementer
Round 4Fresh implementer on the stronger model
Breakergravity refuses a fifth round
Still open at the breakerOutcome
Contestable findingA written ruling, shown in the report
Real but deferrableDeferred, shown in the report
Load-bearing, or a hard gate still failingTask blocked. Tasks depending on it are skipped. All independent tasks still finish

Infrastructure failures don't use a round. A dropped connection retries the same brief, a context limit shrinks the scope, and a test failing in untouched code gets checked against the base.

The two guards that stop an agent gaming the checks

Bar guard

Stops the agent moving the goalposts. Commands come from a copy of the conf pinned when the run started, so test = true in a worktree does nothing. Any change to .gravity/ or declared bar files fails, unless the plan you approved allows it.

Floor guard

Catches skipped or focused tests, deleted tests, changed expected values, suppressions, stubs, empty catch blocks, and paths outside the task. The agent that made the change can't clear a hit. Only your approved plan or a fresh reviewer can, and every countersign reaches you.

How it remembers

One append-only file per run is the only source of truth. Each step writes a line before and after it acts, so a "started" with no result means unfinished. Ledger state always outranks the conversation.

10:02:11  run.start     playbook=standard risk=none base=a1b2c3 gravity=1.0.0 format=1
10:19:40  approve       gate=G1 doc=docs/specs/x.md hash=9f3e by=command
10:41:30  gate          G3 pass tree=e1f2 evidence=evidence/g3.log
10:44:00  task.start    n=1 base=c4d5e6
10:44:02  dispatch      n=1 attempt=1 role=implementer model=sonnet
10:52:40  gate          G4.1 pass tree=a9b8 evidence=evidence/g4-task-1-suite.log
10:58:00  fix.round     n=2 round=1 cause=review
11:10:44  ruling        cost=low what="renamed field to match design" why="design is binding"
11:30:02  task.blocked  n=4 reason="suite fails in x after 4 rounds"
12:01:09  landed        sha=none mode=uncommitted

An approval is bound to what you saw

The agent runs gravity wait, which records the document's fingerprint and stops. When you type /gravity:approve, the hook compares. If the document changed since you saw it, the approval is refused.

A pass is bound to exact code

Each gate line records the tree hash it ran on. Any later change makes that pass stale, and the report check fails until it runs again.

Limits are counted, not remembered

Compaction can cut rules out of memory. So fix rounds live in the ledger and gravity enforces the cap, whatever the agent recalls.

The receipt

Gravity doesn't make the agent smarter. It gives you a receipt for what actually happened, and CI checks that receipt away from the machine that produced it.

You landThe receipt is built from the ledger
You commitIt travels with the code, as a file
PR opensCI runs the checker from the base branch
CompareProven files against the PR head
RerunInstall, tests, lint, types and build, under the base rules
ReportIn the job log and summary

approve      G1 doc=docs/specs/x.md hash=9f3e
approve      G2 doc=docs/plans/x.md hash=7ab1

What it holds, and what it proves

File paths, hashes, gate names and counts. No prose and no data. It lists the tree that was actually proven, so if a merge changed the code, that shows up.

said_done / gates_rejected is how often the agent reported done and a gate then said no. It's the plainest measure of what Gravity is worth.

What CI reports

FindingMeaningResult
Files matchThe code being merged is the code that was provenPass
Changed after proofA proven file differs at the PR headReported fails only under --strict
Not coveredThe PR changes a file no receipt coversReported fails only under --strict
Tests failCommands come from the base branch's conf, so a PR can't change its own rulesFail
No receiptTiny or manual workNeutral

Its limits: a PR can edit the workflow file itself, so that file needs code owners or branch rules. It confirms files and reruns tests, but a forged approval line would still read as valid until approvals are signed. The real-surface check stays local, because CI often lacks that surface.

Scenarios

Click any row to see what happens, step by step. Requests are illustrative.

A full feature"Add CSV export to the reports page, including the billing data"
  1. Router: touches payment data, so Standard plus the security reviewer. One line, overridable.
  2. Ask: it reads the code, then asks only what would change the build, each question with its guess.
  3. Design doc with R1, R2 and so on. Builder check reads it cold. You run /gravity:approve.
  4. Plan with proof per task. plan check passes. You approve again. You can now walk away.
  5. Worktree, baseline green, acceptance checks confirmed not passing yet.
  6. Each task: fresh implementer, red, green, gates, fresh review.
  7. Real surface runs. Whole-branch and security review. One fix wave.
  8. Report built and checked. You read it and type /gravity:land. Changes and a receipt appear uncommitted for you to commit.
  9. On your pull request, CI checks the receipt against the code.
A tiny edit"Fix the typo in the export button"
  1. Router: Tiny. No run, no worktree, no conf needed.
  2. Edit, run the relevant check, report in two lines. There's still no "done" without output.
  3. If a decision appears, it steps up and a run begins.
A bug report"The export drops the last row"
  1. Router: Bug, in a worktree from the start.
  2. Restates the bug in one sentence before reading anyone's theory of the cause, then reproduces it.
  3. Maps the path, lists at most 4 candidates, and scores them by evidence. Nothing Confirmed means no fix, only cheap checks.
  4. Confirmed: shows cause and blast radius. Low risk and reversible continues. Otherwise it waits for your approval.
  5. Failing test recorded, fix, full suite, original symptom gone.
  6. Whole-branch review, report, you land it.
The session dies mid-taskLaptop closes, crash, or usage limit
  1. Nothing relies on cleanup at exit, because there's no dependable exit signal.
  2. Next session: "Run X stopped at task 3. /gravity:resume or /gravity:abandon?" It never resumes alone.
  3. You resume. Ownership moves to this session. Any uncommitted work is saved to a patch and the tree is restored.
  4. An open fix round continues at that round, and the cap still counts.
  5. If the task had committed and its proof still passes, it continues to review. Otherwise it saves a patch, resets and redoes the task fresh.
  6. Each recovery step is safe to repeat, because a crash can hit recovery too.
You change the goal mid-build"Actually, make it PDF rather than CSV"
  1. The test: would the approved design's text have to change? Yes, so the agent may not rule on it.
  2. Stops at the task boundary, or stops the current task and saves its patch. Logs goal.change.
  3. Triages each finished task: keep, revert or modify.
  4. Updates the design and shows you the diff. You approve.
  5. Re-plans from surviving commits in the same worktree. Rulings about files that then change are decided again.
You message mid-buildA clarification, a side question, or "pause"
  1. Clarification that leaves the design's text alone: written as a ruling, and work continues.
  2. Unrelated question or new task: answered without touching the run, or parked as a follow-up in the report.
  3. "Pause": stops at a safe boundary, saves a note, and waits for /gravity:resume.
A hard gate stays blockedTask 4 still fails after 4 rounds
  1. Task 4 is marked blocked. Tasks that depend on it are skipped.
  2. All independent tasks finish.
  3. Any acceptance check for a requirement depending on task 4 becomes "not verified: blocked", so it can't fail G5 for the finished work.
  4. The report says what didn't happen and why.
The agent tries to cheat a checkSkips a test, or loosens the config
  1. Editing the worktree's conf does nothing, because commands come from the pinned copy.
  2. Changing a declared bar file fails G4, unless the plan you approved allows it.
  3. A skipped test, a changed expected value or an empty catch block is a floor guard hit.
  4. Only your approved plan or a fresh reviewer can clear a floor hit, and every countersign appears under Your calls.
The real thing doesn't workAll tasks pass, but G5 fails on the integrated branch
  1. No single task owns it, so it gets one fix wave across all the tasks' files.
  2. Still failing: the run stops at the report, with G5 as the Key signal.
  3. /gravity:land refuses. You can keep the branch or discard it.
Code changes after it passedSomeone edits a file, or a merge alters it, before the PR
  1. The receipt lists each file as it was when G5 and G6 passed.
  2. CI compares those against the PR head and names any file that differs: "changed after proof: auth.ts".
  3. It's reported rather than blocked, since people may change code. A team can turn on --strict to fail the check.
  4. A clean rebase doesn't trigger it, because the comparison is per file.
The plan turns out wrongA step can't work as written, after handoff
  1. gravity halt stops the run.
  2. After /gravity:resume, gravity plan change opens the plan for editing and starts a new generation.
  3. You approve the fixed plan at G2. If the design must change as well, it becomes a goal change.
A feature spans reposBackend plus clients
  1. The design is approved once, upstream, including shared data shapes as the contract.
  2. Each repo gets its own plan, ledger, worktree and report. Upstream goes first.
  3. Downstream runs link to the design, valid only while its fingerprint matches.
  4. Each downstream run's acceptance calls the real upstream, checking URL, shape and auth.
  5. A contract change is a goal change, and only runs whose part changed re-plan.

Skills are tested like code, and the same evals guard every wording change. These are planned. None has run yet, since Gravity isn't built.

How an eval stays honest

Same scenarioPinned model and CLI. No words like "eval" or "test" visible to the agent
Two armsWith Gravity and without it
One judgeScores both arms the same way
From the transcriptWhat was opened and run, never what the agent claims
Complete runs onlyA permission denial is no score

Silent wrong behavior must score worse than honest behavior. A skill firing never counts as a pass by itself. Every wording change needs a recorded failure it fixes.

Still open

The plugin is built and its tool is tested, but it has not yet carried a real feature end to end. These remain.

Decided

1. Design approved
2. Test-first only
3. One question at a time unless independent, at most 4
4. Low-risk reversible bug fixes proceed without approval
5. A fresh agent for each fix round

Live check

Confirmed: subagent hooks carry the owning session, the router returns after compaction, the plugin path resolves in commands and agents.
Not tested: hooks in bypass mode, a plugin upgrade mid-run, a user-level agent replacing a reviewer.

Before team rollout

1. Run real work through each playbook
2. Pressure tests with and without Gravity
3. Seeded-defect test for the reviewers
4. Host the repo and bump the version per release
